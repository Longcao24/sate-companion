## Findings

- **SATE-BE-006** — malformed JSON consumed 3 attempts. processor.py's own comment classifies a 'malformed AI response' as Permanent, but r.json() is parsed OUTSIDE call_ai's try block, so it falls to loop()'s generic `except Exception` and is retried as transient.
- **SATE-BE-009** — a finalize whose RESPONSE was lost leaves the row already finalized, yet the worker still calls requeue_session() — the job returns to `queued` and is processed again (a second paid AI call and a second recordings-bucket copy). No duplicate reaches the user because finalize-session's recording_id guard catches it, but the terminal state IS regressed. Whether requeue_session() itself refuses to move a `done` row could not be verified: the async_processor_state_machine migration SQL is not checked into the repo.
- **SATE-BE-011** — the audio was copied into the recordings bucket 3x — once per retry, each under a NEW timestamped key (3 distinct paths). When the DB write keeps failing, every attempt leaves an orphaned clinical audio object behind and nothing removes them. BE-011 requires the orphan object to be reconciled or safely removed.
- **SATE-SEC-005** — POST /api/firmware is not authorization-gated. The probe reached the handler's input validation (HTTP 400, {'error': 'A version is required (e.g. 1.1.0)'}) rather than an authz check, and in source the route is registered ABOVE the `/admin` block while publishFirmware() never calls isAdmin() — so any authenticated account can publish a fleet-wide OTA image. (This run's caller IS an admin, so the 403 was not expected for them; the defect is proven by the missing gate in code plus the handler being reached. Confirming it empirically needs a second, non-admin account.)
- **SATE-BE-012** — retrySession() resets attempts to 0 and nulls process_error, so the previous failure is no longer traceable on the row — BE-012 requires 'previous failure remains traceable' / an audit record of the retry.
- **SATE-SEC-007** — no audit-trail table is reachable (sate_audit_log=404, audit_log=404, sate_events=404, session_audit=404) — deletions and retries leave no auditable record, which SEC-007 and BE-012 both require.
- **SATE-WEB-005** — `recordings.updated_at` did not change when the transcript was rewritten — the column exists but nothing maintains it, so even 'when was this last edited' is not answerable from the row.
- **SATE-WEB-005** — the edit overwrites `recordings.transcript` in place. There is no version column and no history table (recording_versions=404, transcript_versions=404, recording_history=404, transcript_history=404). Undo/redo lives only in the browser's localStorage (`historyService.ts`, key `transcript_history_<id>`, capped at 50 states), so history is per-browser, invisible to anyone else, and lost on cache clear, a different device, or another user opening the same recording. WEB-005 asks for versioning of a saved transcript; the server keeps exactly one version.
- **SATE-WEB-006** — writer B's save (HTTP 200) silently overwrote writer A's — final text is 'writer B'. Saves go straight to PostgREST with no version check, no If-Match/ETag and no updated_at precondition, so two clinicians editing the same transcript lose one set of edits with no warning and no way to recover it (there is no server-side history to recover from).
