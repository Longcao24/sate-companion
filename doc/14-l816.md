# 14 — SATE L816 handheld recorder

The **SATE L816** is SATE's name for an L816 handheld (the "2837 protocol family" of BLE
voice recorders) — a device family SATE Companion can drive directly: find it over BLE,
start and stop a recording on it, pull the finished take off its storage, convert the
audio, and push it through the same upload path as everything else. No vendor app, no
vendor cloud account.

**The product name and the advertised name are not the same thing, on purpose.** The
hardware's radio says `L816`; everywhere a user can read it, it is a **SATE L816**. The
one string lives in `L816_DISPLAY_NAME` (`src/l816/L816Link.ts`) and is what a paired unit
is remembered as, so Home and the connect screen cannot drift. The scan matcher still
looks for the advertised `L816`, and the scan list still shows the raw name it heard —
that list is diagnostics, and "what my phone actually hears" is exactly what tells a user
whether they are looking at their own recorder.

It is the mirror image of Plaud. Plaud is iOS-only because its SDK is an arm64 **iOS**
binary; the L816 is **Android-only** because its codec is an ARM **Android** binary. Both
gates are hardware facts, not preferences.

---

## 1. Where it plugs in

```
L816 (BLE GATT)
  └── src/l816/L816Link.ts        protocol: scan, connect, record, list, download
       └── modules/sate-asc        ASC-VI -> WAV  (vendor .so via JNI, Android only)
            └── api.uploadSession  POST /api/sessions, device_serial `l816-<MAC>`
                 └── device-api -> cf-processor -> AI -> `recordings`
```

| File | Responsibility |
|------|----------------|
| `src/l816/L816Link.ts` | The whole BLE protocol: `55 AA`/`AA 55` framing, opcodes, three notify subscriptions, download assembly, byte-exact completion |
| `src/l816/L816Store.ts` | Paired L816s in AsyncStorage (no binding, no lock concern — same as the pendant) |
| `src/screens/L816ConnectScreen.tsx` | Scan → connect → record/stop → download → upload; plus the device's own file list as a recovery path |
| `src/components/L816DeviceCard.tsx` | The device likeness used on Home and in the "Add a device" sheet |
| `modules/sate-asc/` | The ASC-VI decoder (Kotlin + the vendor JNI binaries) |
| `src/features.ts` | `L816_ENABLED` — Android **and** the decoder actually loaded |
| `L816_DISPLAY_NAME` | The one place the product name `SATE L816` is written |
| `src/ble/radio.ts` | The `l816` radio owner |

The SATE L816 is a full member of the unified device registry (`useManagedDevices`), so a
paired unit shows on Home as a row like any other device, with `kind: "l816"`.

## 2. Why this is Android-only

The SATE L816 does **not** send PCM and does not send a container format. Every take is a
stream of **ASC-VI frames**: 82 bytes = 41 little-endian `int16` words, word 0 a header
and words 1..40 a payload that decodes to **320 samples (20 ms @ 16 kHz mono)**.

The only decoder that exists is a pair of proprietary binaries from the vendor's
reference APK — `libasc_dec.so` (the codec) and `libASCDecoder.so` (the JNI shim, which
`dlopen()`s the first at init). They are ARM ELF shared objects for Android
(`arm64-v8a`, `armeabi-v7a`). They cannot load on iOS, and they cannot run in the x86
`cf-processor` container either, so the conversion has to happen on the phone — and only
on an Android phone.

```ts
export const L816_ENABLED = Platform.OS === "android" && isAscAvailable();
```

The second half of that check matters as much as the first: the binaries are git-ignored
(`modules/sate-asc/android/src/main/jniLibs/`, same treatment as the Plaud frameworks), so
a fresh clone builds and runs fine — it just must not offer hardware whose recordings it
could download and then never convert or upload. Copy them in per
`modules/sate-asc/README.md`.

> **Do not rename `com.actions.asc.jni.ASCDecoder`.** The binary exports
> `Java_com_actions_asc_jni_ASCDecoder_decode` and friends, so the symbols only resolve
> for a class at exactly that fully-qualified name. Moving it fails with an
> `UnsatisfiedLinkError` at the first `decode()` — not at load — so it looks like a codec
> bug rather than a packaging one.

If the codec is ever reverse-engineered or the vendor supplies source, `modules/sate-asc`
is the only thing that has to change. `L816Link.ts`, the screen and the upload path are
all portable TypeScript that would run on iOS unchanged.

## 3. BLE profile

UUID suffix `-2233-4455-6677-889912345678`.

| Prefix | Role |
|--------|------|
| `0011200a` | Service |
| `0011201a` | Notify — record events **and file data** |
| `0011202a` | Write **without response** — commands |
| `0011203a` | Notify — command responses |
| `0011204a` | Notify — transferred ASC bytes |

**Enable all three notifies, in the order `1203a → 1204a → 1201a`.** With only the first
two enabled, transfers stall on this firmware. `1201a` is not decorative — file bytes
arrive on it as well as on `1204a`, so both feed the same assembler.

Scanning runs with **no service filter**: the L816 does not reliably advertise its service
UUID, and the name can be a stale cached GAP name. The link matches on name *or* the
advertised service, and the screen also lists every peripheral heard so the user can pick
theirs manually.

The reference prototype fell back to one hardcoded MAC. That is not done here — a paired
unit is remembered in `L816Store` and reconnected by id.

## 4. Packet format

- Request `55 AA <len> <opcode> <payload>`, response `AA 55 <len> <opcode> <payload>`.
- Normally total bytes = `len + 3`.
- **Legacy length exceptions, and they are the whole ballgame for the parser:** opcode
  `03` declares `0x0F` but carries a 17-byte name; opcodes `04`, `05`, `07` declare `0x13`
  but carry a 17-byte name **and** a 4-byte size. Each is three bytes longer than the
  formula. Miss this and the parser loses every packet after the first one, which on
  screen looks exactly like a dead device.
- Names are `NN_yyyyMMddHHmmss`, 17 ASCII bytes. Sizes/offsets are **uint32 big-endian**.
- A notification is **not** necessarily one whole packet, and may contain more than one.
  Buffer and re-scan on every arrival.

| Action | Packet |
|--------|--------|
| Query state | TX `55 AA 01 0F` → RX `AA 55 02 0F 02` (`02` = idle) |
| Sync clock | TX `55 AA 0F 02 <14 ASCII digits>` → RX opcode `02` |
| Start | TX `55 AA 01 03` → RX `AA 55 0F 03 <name17>` |
| Stop | TX `55 AA 01 04` → RX `AA 55 13 04 <name17> <sizeBE32>` |
| List | TX `55 AA 01 05` → RX `AA 55 13 05 <name17> <sizeBE32>` per entry, then `AA 55 01 06` |
| Download | TX `55 AA 13 07 <name17> 00 00 00 00` → RX `AA 55 13 07 <name17> <bytesBE32>`, data, then `AA 55 01 09` |
| Cancel | TX `55 AA 01 08` |
| Device error | RX opcode `>= 0xFB` (`FD` is the one seen in practice) |

Note the download request declares length `0x13` (19) although it carries 21 bytes —
mirroring the device's own quirk is what makes it accept the request at all.

---

## 5. The four rules that make a transfer trustworthy

1. **The ack size is the transfer size, never the list size.** They differ by design: a
   take listed as 204 332 transfers 26 158 bytes. Validate against the opcode-07 ack.
2. **Complete only on EOF *and* an exact byte match.** A take that merely stopped arriving
   is a truncated recording, and a truncated recording that uploads successfully is
   indistinguishable from a real one.
3. **A size that is not a multiple of 82 is refused up front**, before spending a minute
   transferring something the decoder cannot read.
4. **After Stop: wait 1 500 ms → re-list → match the exact name Stop returned → wait
   600 ms → download.** An immediate download comes back as error opcode `FD`; the device
   is still flushing. And never "the last entry in the list" — that is a different take
   the moment anything else is on the device.

Nothing is deleted from the L816. A take whose upload failed is still on the hardware and
still in the on-screen list, which is the recovery path.

## 6. Naming and the serial

`device_serial` is `l816-<MAC with separators stripped>` — e.g. `l816-8470D00F660E`. The
serial ends up in a storage key (`<user>/<serial>/<id>.wav`), so the colons come out in
`l816Serial()` rather than in an object path.

`session_number` is the take's own timestamp (`NN_yyyyMMddHHmmss` → unix seconds), not the
upload time. It is stable across a retry, so re-uploading the same take dedups instead of
duplicating — see `storeSessionRecord`'s idempotency probe on
`(user, serial, patient, session_number, bytes)`.

That makes the L816 the third family that puts a **timestamp** where the recorder puts a
take number, so the web label rule (`src/services/recordingName.ts`) handles it alongside
the pendant and Plaud: `l816` → **`L-3:17 PM`**.

## 7. Radio ownership

The L816 is plain `react-native-ble-plx` on the **shared** `BleManager`, like the pendant
and unlike Plaud. It has the logical owner `l816` in `src/ble/radio.ts`:

- SATE ↔ Pendant ↔ L816 handoff is **`stopScan()` only, never destroy** (RULE #2).
- `acquireRadio("l816")` is called synchronously in `openL816` in `App.tsx`, never in an
  effect.
- Leaving the screen calls `l816.teardown()` — stops the scan and drops the connection,
  without touching the shared manager.

There is no binding and no lock concern anywhere in this family (RULE #1 is a Plaud rule).

## 8. Recording started ON THE DEVICE

The take a user cares about most is often the one they start by pressing the button on the
hardware with the phone in a pocket. That take must reach SATE without anyone opening a
file list, so the link watches for it and the screen downloads and uploads it with no tap.

Two independent signals, because only one of them is guaranteed:

| Signal | Latency | Gives a file name? | Reliable? |
|--------|---------|--------------------|-----------|
| An **unsolicited** opcode `03`/`04` pushed by the device | instant | yes | **Unproven** — no capture from the reference unit shows one |
| The **state poll** (`STATE_POLL_MS`, 3 s) — the same read-only opcode `0F` the connect handshake already sends | ≤ 3 s | no | yes |

`settle()` returns a boolean for exactly this reason: an opcode `03`/`04` that **no waiter
was expecting** is by definition something the user did on the device, and it becomes an
`L816DeviceEvent`. Keep that boolean — swallowing an unmatched response is how the feature
silently disappears.

The poll only sees the state *flip*, never a name, so a `stopped` event with no `file`
sends the screen to `fetchNewSince(knownNames)`, which diffs the file list. Diffing beats
"take the last entry": these devices do not list in a guaranteed order, and if two takes
appeared the newest-by-name wins while the rest stay in the list.

**The poll never runs while a command, a listing or a transfer is in flight.** Interleaving
a state query into a download is how you corrupt one.

Related: bytes arriving on `1201a`/`1204a` with **no transfer running** are now logged
rather than dropped (`[L816] notify outside transfer …`). The reference app discards them,
but `1201a` is named *"Record Notify"* in the vendor's own documentation — if the device
does announce a button press somewhere, that is the likeliest channel and nobody has
looked. Watch that log line on real hardware.

## 9. What the vendor app proves the device can do

The vendor app (`AI_DVR_Link-3.2.0.apk`) is **Flutter**, so the protocol is not in the dex —
it is Dart AOT inside `lib/arm64-v8a/libapp.so`. The Dart symbol names survived, and the
command classes in `dvrlink_bluetooth/xlx_link/protocol/command/` map **one-to-one** onto
the opcodes we reverse-engineered from the wire. That correspondence is the useful part: it
independently confirms our whole protocol map, and it names the commands we never captured.

| Opcode | Our name | Vendor class |
|---|---|---|
| `0x02` | sync clock | `SyncTimeRequest` / `SyncTimeResponse` |
| `0x03` | start | `StartRecRequest` / `StartRecResponse` |
| `0x04` | stop | `EndRecRequest` / `EndRecResponse` |
| `0x05` | list | `GetFilesRequest` / `GetFilesResponse` |
| `0x06` | list end | `GetFilesEndResponse` (+ `GetFilesFailResponse`) |
| `0x07` | download | `SyncFileRequest` / `SyncFileResponse` |
| `0x08` | cancel | `EndSyncRequest` / `EndSyncResponse` |
| `0x09` | EOF | `SyncCompleteResponse` (+ `SyncFailResponse`) |
| `0x0F` | state | `RecStRequest` / `RecStResponse` |
| **?** | **delete** | **`DeleteRequest` / `DeleteResponse` / `DeleteFailResponse`** |

**Commands the device supports that we have never used:** `BatteryRequest`,
`StorageRequest` / `StorageTotalResponse` / `StorageRemindResponse`, `VersionRequest`,
`GetMacRequest`, `PauseRecRequest`, `LedSwRequest`, `OTARequest`, `DFURequest`,
`NoiseSwResponse`, `DecibelResponse`.

### Deleting a file on the device — not yet

A delete command **exists** for this family. Its **opcode byte does not appear in any
string**, and it cannot be inferred: the order of class names in the binary is not
declaration order (`SyncFileRequest` 0x07 precedes `EndRecRequest` 0x04, which precedes
`StartRecRequest` 0x03), so position proves nothing. It was tested and refuted rather than
assumed.

🛑 **Do not guess it.** The device holds the only copy of a recording until it is uploaded,
and an unknown opcode could erase more than one file or wedge the unit. The one certain,
cheap way to learn it is a **Bluetooth HCI snoop capture** of the vendor app deleting a
single file — it yields the exact `55 AA` write on `0011202a`, with its payload, in one
attempt. Deeper Dart AOT reverse-engineering (e.g. `blutter`) is the alternative and is
hours of uncertain work.

#### Capturing it (Pixel 9 / Android 16, no root needed)

The snoop log lives at `/data/misc/bluetooth/logs/btsnoop_hci.log`, which is **not
readable without root** — but `adb bugreport` bundles it, and that works on a normal
device.

1. **Force-stop SATE Companion.** The L816 talks to one phone/app at a time; if our app
   holds the link the vendor app cannot connect.
   ```sh
   adb shell am force-stop com.auspexmedix.satecompanion
   ```
2. **Settings → System → Developer options → Enable Bluetooth HCI snoop log → Enabled.**
   (On some builds it is a three-way dialog: Disabled / Filtered / Enabled — pick
   **Enabled**, "Filtered" strips the payloads we need.)
3. **Toggle Bluetooth off and on.** The setting only applies to a fresh stack, and this
   also starts a clean log.
4. In **AI DVR Link**: connect to the L816 and **delete exactly ONE recording** — pick a
   throwaway take, because this one really is deleted. Doing only one delete is what makes
   the result unambiguous.
5. Pull the log:
   ```sh
   adb bugreport l816-delete.zip
   unzip -o l816-delete.zip -d l816-delete
   find l816-delete -name 'btsnoop_hci*'
   ```
6. Read it:
   ```sh
   python3 doc/l816-find-delete-opcode.py l816-delete/FS/data/misc/bluetooth/logs/btsnoop_hci.log
   ```
   It prints every `55 AA` / `AA 55` frame in order, names the opcodes we already know, and
   flags the one we do not. A file-scoped command carries the 17-byte
   `NN_yyyyMMddHHmmss` name, which the script decodes — that is the confirmation that the
   unknown frame is the delete and not something incidental.
7. **Turn the snoop log back off.** It records every Bluetooth packet on the phone,
   including other devices.

The capture also answers the second question for free: whether delete is acknowledged
(`DeleteResponse`) or can fail (`DeleteFailResponse`), and whether the device re-lists
afterwards — all of which the implementation needs in order to be safe.

Until then nothing is lost by not deleting: the device keeps every take, the app lists them
all, and a failed upload stays recoverable from that list. Storage filling up is the only
cost.

## 10. Staying connected in the background (Android)

Detecting a take started on the device's own button is worth nothing if it only works
while someone is staring at the screen — the whole point is the phone in a pocket. But
**Android stops scheduling a backgrounded app**, which kills the 3 s state poll and any
transfer in flight.

So while an L816 is connected the app runs an Android **foreground service**
(`modules/sate-fgservice`). The service does no Bluetooth work: the BLE link, the L816
protocol and the upload all stay in JavaScript where they already live and are already
tested. Its only job is keeping the process alive so the existing code keeps running.

- The ongoing notification is **not decoration** — Android requires one for a foreground
  service, and it is also the user's only status readout while they are elsewhere. It
  mirrors the real state: waiting / recording / downloading `n%` / uploading.
- **Only the download gets a progress bar**, because only it has a byte count. Everything
  else shows text and no bar.
- A finished transfer posts a **dismissible** notification. That is the only way the user
  learns a take arrived without opening the app — and a **failure** notifies too, because
  silence there would leave them believing a recording is safe when it is still only on the
  device.
- `POST_NOTIFICATIONS` is requested on connect (Android 13+). Declining costs the
  background link, not recording.

**What it does not do, deliberately:**

| Situation | Behaviour |
|---|---|
| App backgrounded, L816 screen open | **Keeps working** — poll, transfer, upload |
| App swiped away from recents | **Stops.** `onTaskRemoved` clears the notification |
| Killed by Android under memory pressure | Stops. `START_NOT_STICKY` |
| User navigates back to Home in the app | Link drops (radio arbiter) and the service stops with it |
| iOS | Not supported — a backgrounded iOS app keeps its BLE connection but its JS timers are suspended, so the poll cannot run |

Both of those "stops" are choices. `START_NOT_STICKY` and stopping on task removal mean
Android never revives a service with no JavaScript behind it — a notification claiming a
live connection that nothing is holding is worse than no notification.

The permissions and the `<service>` live in the module's **own** `AndroidManifest.xml`,
which merges into the app's. They cannot go in `app.json`'s android block or in `android/`
— that directory is git-ignored and regenerated by `expo prebuild`.

## 11. The web app

**Nothing about processing is L816-specific, and that is the design.** The phone converts
ASC-VI to a plain 16 kHz mono 16-bit WAV *before* anything leaves it, so what reaches
`POST /api/sessions` is byte-for-byte the same shape the pendant already sends. From there
it is the one pipeline: `sate_device_sessions` → `cf-processor` (duration guard, RMS guard,
the AI call) → `finalize-session` → a `recordings` row the web app renders like any other.
No branch in `cf-processor` or `finalize-session` looks at `device_serial`.

The take lands as `device_l816-<MAC>_s<timestamp>.wav`, which `recordingName.ts` labels
**`L-3:17 PM`** — verified by running the real `recordingLabel()` / `sessionLabel()`, which
agree with each other, and still return a human-typed name untouched.

⚠️ **What the web does NOT get is a device ROW.** `GET /api/devices` returns `sate_devices`
rows only, and an L816 has none — same as Plaud and the pendant. `ManagedDevice.kind` is
declared and branched on in `DeviceCard`/`DevicePanel`, but **nothing populates it**, so
that branching is unreachable today. This predates the L816 and is not specific to it: an
external recording reaches the web as a session and a recording, never as a piece of
hardware you can see. If the server ever synthesizes those rows, the branches are already
correct for `'l816'`.

## 12. Things the device does that surprise people

- **It keeps recording when the app closes or goes out of range.** Reconnecting can land
  straight in a recording state; `connect()` queries opcode `0F` and the screen picks the
  state up rather than assuming idle. The timer then counts from the reconnect and says
  so, because the device does not report elapsed time.
- **Stopping is not the end of the take.** The transfer afterwards is, and it can take
  longer than the recording did. "Stop" and "uploaded" are separate states on screen.
- **Only the download can be measured.** Waiting, listing and decoding get a message and
  no progress bar — a bar creeping forward on a guess turns "I don't know how long this
  takes" into a promise.
- **Only one phone at a time.** If the vendor app holds the connection, the L816 will not
  be found.
- **Resume is not implemented.** A failed transfer is repeated from offset zero.
- **Its clock lies.** The reference unit lists `01_20821119193921` — year 2082 — next to
  takes from 2022. That value becomes `session_number`, and 3.5e9 does not fit a 32-bit
  integer column, so `takeTimestamp()` clamps anything outside 2000..(now + 1 day) back to
  now. The device's own file name is still shown beside the take.

## 13. Verified

The protocol here was ported from a standalone Android prototype that was validated live
against a real L816 and a Pixel 9 / Android 16: recording started and stopped remotely,
the exact filename matched, 20 664 ASC bytes downloaded, decoded to 161 324 WAV bytes,
16-bit mono 16 kHz, 5.04 s playable.

**The port into SATE Companion has not itself been run against hardware** — this machine
has no JDK or Android SDK, so the Kotlin module has not been compiled either. Build with
`npx expo run:android` on a machine with the Android toolchain and test against a real
L816 before relying on it.
